\chapter{A Case Study: NYC Crashes}


Every day, New Yorkers travel across the city in countless ways:
walking to school, biking to work, driving across town, or riding
buses and subways. Most of these journeys end safely, but some result
in crashes that cause injuries, delays, and sometimes fatalities. Can
data help us understand when crashes occur, where they are most
common, and what factors are associated with them? In this chapter, we
investigate these questions using a real dataset from NYC Open Data,
applying ideas from throughout this book: importing and cleaning data,
exploring patterns with tables and graphs, working with dates and
times, handling missing values, and interpreting results carefully.

\section{Missing Values and Data Quality}

With the data imported, renamed, and filtered to the target week, we
turn next to a closer look at what is missing from it. Missing
values\index{missing value} are not just empty spaces. They are clues about how the
data were collected. A missing borough or zip code might mean the crash
happened on a highway, at an unusual address, or in a record where the
location was not entered completely.

We start with the borough\index{borough} column. The function \lstinline{trimws()} removes
extra spaces at the beginning and end of each entry. Then we convert
blank borough names into \lstinline{NA}, R's missing-value marker\index{missing value!NA@\lstinline{NA}}.

\showChunk{R}{Code/nyc_crashes.R}{borough_clean}

Zip codes\index{zip code} can also have impossible values. If the zip code column is
numeric, a zero should not be treated as a real New York City zip code,
so we recode it as missing.

\showChunk{R}{Code/nyc_crashes.R}{zip_clean}

Now we count missing boroughs, missing zip codes, and rows where both
are missing.

\showChunk{R}{Code/nyc_crashes.R}{missing_counts}

Try the code above. What do you see? How many rows have a missing 
borough, a missing zip code, or both?
The cross-tabulation shows that missing boroughs and missing zip codes
go together perfectly in this week: every row with a missing borough
also has a missing zip code. That pattern suggests the location was not
entered at all, not that one piece was forgotten.

Location coordinates need their own check. New York City latitudes\index{latitude} are
around 40 degrees north, and longitudes\index{longitude} are around 74 degrees west.
Coordinates such as \lstinline{(0,0)} are not in New York City. We mark
coordinates as bad if they are zero-like or outside a broad box around
the city.

\showChunk{R}{Code/nyc_crashes.R}{geo_bad}

After counting the bad coordinates, we replace them with \lstinline{NA}.
Then we count rows where either latitude or longitude is missing.

\showChunk{R}{Code/nyc_crashes.R}{geo_recode}

Sometimes a row has latitude and longitude but no zip code. In that
case, we might be able to fill in the zip code later by using a map. We
create \lstinline{fillable_zip} for rows with missing zip codes and
present coordinates.

\showChunk{R}{Code/nyc_crashes.R}{fillable_make}

To compare days of the week, we create a weekday variable\index{weekday}. The
\lstinline{levels} argument puts the days in calendar order instead of
alphabetical order. We use this same variable again later in the
chapter, when we compare business days and weekends.

\showChunk{R}{Code/nyc_crashes.R}{weekday}

Now we count fillable zip codes by weekday and calculate the
proportion for each day. \lstinline{tapply()} does this in one step:
it splits \lstinline{fillable_zip} into groups by \lstinline{weekday}
and applies \lstinline{mean()} within each group.

\showChunk{R}{Code/nyc_crashes.R}{fillable_table}

You should see the following:

\inlnR{```print(table(df$weekday, df$fillable_zip))```}[nyc-fillable][vbox]

\subsection{The Midnight Artifact}

There is also a data quality question hiding in the time values. Many
crashes are recorded exactly at midnight or exactly on the hour. That
may mean the actual crash times were rounded during reporting,
or that a default value was used.

\showChunk{R}{Code/nyc_crashes.R}{rounded_times}

\inlnR{```cat(round(100 * mean(df$minute == 0, na.rm = TRUE),
1))```}[nyc-onhour-pct]\%
of the crashes are recorded on the hour, far more than we would expect
if crash times were spread uniformly across minutes. The spike at hour
0 is especially suspicious:
\inlnR{```cat(sum(df$hour == 0, na.rm = TRUE))```}[nyc-hour0-count]
crashes are recorded there, and
\inlnR{```cat(sum(df$hour == 0 & df$minute == 0,
na.rm = TRUE))```}[nyc-midnight-count]
of those are recorded at exactly 00:00. That pattern is hard to explain
with real traffic: it is much more likely that a missing or unknown
crash time was entered as the default value 00:00:00. If we ignored
this, we might conclude that midnight is one of the most dangerous
hours of the day, when the truth is that many of those crashes simply
happened at some unknown time.

The exact-midnight rate is not the same in every borough. A higher rate
in one borough could mean weaker data-quality control there, or simply
that small boroughs have more variable rates because they have fewer
crashes.

\showChunk{R}{Code/nyc_crashes.R}{midnight_by_borough}

Try the code above. You should see the following:

\inlnR{```print(round(midnight_rate_by_borough, 3))```}[nyc-midnightrate][vbox]

Staten Island has the highest share of exact-midnight crashes in this
week, but it also has the smallest number of crashes overall, so the
rate is based on only two records. The pattern is still worth watching
across a longer time window.

To see how misleading the default entries can be, we can reassign the
crashes recorded at exactly 00:00 uniformly at random within each
borough. This is not a claim about when those crashes really happened;
it is a way to show how much the midnight peak depends on a data-entry
choice.

\showChunk{R}{Code/nyc_crashes.R}{hour_corrected_make}

Figure~\ref{fig:ch9:hourcorrected} compares the original hourly counts
by borough with the counts after the exact-midnight crashes have been
redistributed within each borough. The two panels come from a single
\lstinline{par(mfrow = c(1, 2))} call, which tells R to arrange the
next two plots side by side instead of one after another. The
midnight spike shrinks dramatically.

\showChunk{R}{Code/nyc_crashes.R}{hour_corrected_plot}

\begin{figure}[H]
\includegraphics[width=0.95\textwidth]{images/chapter_9/crashes_by_hour_corrected.pdf}

Rounding is not automatically bad, but it changes what we should say.
If many times are rounded or defaulted, we should be cautious about

\section{Crash Severity}

Having looked at when crashes happen, we turn now to how bad they
are: a first step toward our ``what factors'' question. The dataset
records injuries and deaths separately.

\subsection{Defining a Severe Crash}

Before using those numbers, we check one internal consistency
relationship: the total number of persons injured should equal the
sum of pedestrians, cyclists, and motorists injured. The same should
hold for deaths.

\showChunk{R}{Code/nyc_crashes.R}{injury_consistency}

\inlnR{```cat(sum(df$number_of_persons_injured != df$injured_sum,
na.rm = TRUE))```}[nyc-injmismatch]
rows report injured persons without reporting any injured pedestrians,
cyclists, or motorists, and
\inlnR{```cat(sum(df$number_of_persons_killed != df$killed_sum,
na.rm = TRUE))```}[nyc-killmismatch]
rows show the same pattern for deaths. The totals and the subtotals do
not always match, which is a reminder that real data can contain
internal inconsistencies. For our severity rule we use the total
counts, because those are the broadest measure available.

For a first look, we call a crash severe\index{severe crash} if at least one person was
injured or killed. This is a simple rule, not the only possible rule.

\showChunk{R}{Code/nyc_crashes.R}{severity_make}

Now we count severe crashes and calculate the proportion of all crashes

\inlnR{```cat(round(100 * mean(df$severe, na.rm = TRUE), 1))```}

harder to under-report. A higher proportion late at night could

and plots do, however, give us a first look at the data and help us
formulate questions for further study.

Together, these results give a first answer to all three questions
from the start of the chapter. Crashes are not spread evenly across
the day or week --- they cluster in the late morning and evening, and
are more common on business days and during business hours. They are
not spread evenly across the city either: crash counts differ sharply
by borough throughout the tables above, with Brooklyn and Queens
consistently seeing the most crashes and Staten Island the fewest.
Raw counts like these mostly reflect exposure, not risk: Brooklyn and
Queens also have far more residents, workers, and visitors moving
through them than Staten Island does, so a fair comparison would need
a rate, not just a count. Figure~\ref{fig:ch9:locations} shows both
severe and not-severe crashes clustering in the same dense areas
rather than in different parts of the city. And severity itself
relates to several factors, rising somewhat with the number of
vehicles involved and shifting across the hours of the day. These are
patterns, not proof. The next section asks whether some of them hold
up to formal statistical scrutiny.

\section{From Description to Inference}

The descriptive tables above invite a few simple inferential checks.
Because severity is a yes-or-no outcome, the appropriate comparison is
not a t-test. In this section we use three tools: a chi-squared test
to compare severe and non-severe crashes across day types, a binomial
confidence interval to estimate the overall severe-crash rate, and a
logistic regression model to see how severity relates to several
predictors at once.

\subsection{Chi-Squared Test of Independence}

We can compare the 2-by-2 table of severe and non-severe crashes on
business days and weekends with Pearson's chi-squared test of
independence\index{chi-squared test of independence}. That test works with counts, which is
the right scale for this data.

\showChunk{R}{Code/nyc_crashes.R}{severity_inference_table}
\showChunk{R}{Code/nyc_crashes.R}{severity_chisq}

The contingency table is
\inlnR{```tab_business_severe```}[nyc-sev-tab][vbox]
and the chi-squared test gives a p-value of
\inlnR{```round(chisq_business_severe$p.value, 4)```}[nyc-sev-p].
For this week, the evidence is not strong enough to say that severe
crashes differ by day type.

\subsection{A Confidence Interval for the Severe-Crash Rate}

We can also estimate the overall severe-crash rate for the week. The
point estimate\index{point estimate} is \inlnR{```round(severe_rate, 3)```}[nyc-sev-rate],
and the exact 95\% binomial confidence interval\index{confidence interval!binomial} is
\inlnR{```round(severe_rate_ci$conf.int[1], 3)```}[nyc-sev-lo]
to \inlnR{```round(severe_rate_ci$conf.int[2], 3)```}[nyc-sev-hi].
This interval is a direct estimate for a binary response; it does not
rely on a normal approximation for the raw crash outcomes.

To make the binomial calculation concrete, here are the raw counts of
severe and non-severe crashes used by the binomial test:

\showChunk{R}{Code/nyc_crashes.R}{severity_binom_table}

The table shows
\inlnR{```sum(df$severe, na.rm = TRUE)```}[nyc-sev-count]
severe crashes and
\inlnR{```sum(!df$severe, na.rm = TRUE)```}[nyc-nonsev-count]
non-severe crashes. The point estimate reports the fraction of crashes
in this sampled week that were classified as severe. The exact binomial
confidence interval gives a range of plausible values for that
underlying proportion. A narrow interval means the estimate is relatively
stable (we observed many crashes); a wide interval means more sampling
uncertainty (fewer crashes). These values describe the observed week and
should not be interpreted as causal effects.

\section{Recommendations for the Open Data Team}

Open data releases are only as useful as their quality allows. In this
single week we found several patterns that are worth flagging for the
NYC Open Data team.

\showChunk{R}{Code/nyc_crashes.R}{publisher_summary}

\begin{itemize}
\item
  \textbf{Default crash times.} About
  \inlnR{```round(100 * prop_on_hour, 1)```}[nyc-prop-on-hour]\% of
  records have a time ending in ``:00'', and
  \inlnR{```n_exact_midnight```}[nyc-exact-midnight] are recorded at
  exactly 00:00. Those exact-midnight entries are almost certainly a
  default value for missing times, not real midnight crashes. A missing
  time should be coded as missing rather than as 00:00:00.
\item
  \textbf{Missing location fields.} In this week,
  \inlnR{```n_both_missing```}[nyc-both-missing] rows are missing both
  borough and zip code, and the two fields are missing together in every
  case. A single missing-location flag would be clearer than separate
  blank columns.
\item
  \textbf{Internal consistency of injury counts.}
  \inlnR{```n_injury_mismatch```}[nyc-injury-mismatch] rows report a
  positive total number of persons injured while reporting zero injured
  pedestrians, cyclists, and motorists. Either the total or the
  subtotals are in error; the form or the validation rules should ensure
  they agree.
\item
  \textbf{Vague contributing factors.} Vehicle 1 has
  \inlnR{```n_unspecified```}[nyc-n-unspecified]
  \lstinline{unspecified} entries. This category is too vague to support
  policy decisions. Either removing it from the pick-list or requiring a
  more specific follow-up would improve the data. We keep
  \lstinline{other vehicular} as a separate catch-all, but a more
  detailed breakdown would be better.
\item
  \textbf{Standardized vehicle types.} The vehicle type columns are
  free-form text. Consolidating entries into a controlled vocabulary or
  at least cleaning common misspellings would make the data much easier
  to summarize.
\item
  \textbf{Drop or document redundant columns.} The
  \lstinline{location} column is a text copy of latitude and longitude.
  Keeping it invites inconsistencies; storing only the numeric
  coordinates is cleaner.
\end{itemize}

These recommendations are based on one week of data, so they describe
patterns rather than prove systemic problems. Still, each is easy to
investigate across the full dataset and each would make the published
data easier for analysts, journalists, and citizens to use correctly.

\section{Summary}

This case study used the same habits we have practiced throughout the
book. We loaded a dataset, checked its shape, cleaned names, converted
dates, filtered rows, looked for missing values, created new variables,
and compared groups with tables and proportions.

The biggest lesson is not a single fact about New York City traffic. The
lesson is the workflow. Real datasets need careful questions at every
step: Did the file load? Are the dates right? Are missing values coded
consistently? Do the variables mean what their names suggest? Are we
describing a pattern, or are we claiming a cause?

Open data makes these questions available to anyone with patience and a
computer. City agencies, federal agencies, scientific groups, sports
leagues, and many other organizations share data that students can
explore. NYC Open Data is a good place to look for more examples. In
addition to crash records, it includes widely used datasets such as 311
Service Requests, which record calls and online reports about noise,
heat, street conditions, trash, and many other city services. With the
tools from this book, you can begin with one clear question, check the
data carefully, and build an honest answer one step at a time.
